# Flagpole

Flagpole is a feature flag service. Teams create flags, turn them on environment by environment, and target them with rules and percentage rollouts. Changes to protected environments go through a review that someone else approves. Applications read flags with an SDK key, and every change streams to them as it happens.

It's built on [Zinc](https://github.com/0mjs/zinc) 0.7, with Postgres, Redis and Kafka (Redpanda), and a React dashboard.

Flagpole is Zinc's playground: the [cookbook](https://zinc.carbonsoft.sh/cookbook/production/) grown into a whole app, so you can see Zinc's features working together in a real system instead of one at a time. Typed handlers, generated OpenAPI with role scopes, groups and guards, sessions, CSRF, server-sent events and Zinc's middleware all run here, tested end to end. [Zinc in use](#zinc-in-use) lists where each one is.

## Run it

You need Docker, Go 1.26+ and Node 22+.

```sh
make up       # Postgres, Redis, Redpanda, Redpanda Console, Mailpit
make seed     # empty the database and load the demo data
make api      # the API on :8080
make worker   # the outbox relay and Kafka consumer
make web      # the dashboard on http://localhost:5173
```

Or run the whole thing in containers, with the dashboard on http://localhost:3000:

```sh
make app
docker compose --profile app run --rm --entrypoint flagpole api migrate reset
docker compose --profile app run --rm --entrypoint flagpole api seed
```

| URL | What |
| --- | --- |
| http://localhost:5173 | Dashboard (dev server) |
| http://localhost:8080/docs | API reference, generated by Zinc from the handlers |
| http://localhost:8080/openapi.json | OpenAPI 3.1 spec |
| http://localhost:8080/metrics | Prometheus metrics |
| http://localhost:8025 | Mailpit: invite and password reset emails |
| http://localhost:8081 | Redpanda Console: the Kafka topics |

The seed creates four people, one for each role: `ada@example.com` (admin), `linus@example.com` (approver), `grace@example.com` (editor) and `vera@example.com` (viewer). `make seed` prints their password, and the sign-in page lists them in development. It also creates two projects with five flags, a change request waiting for review, an SDK key for `web-app` production (printed by the seed), and two days of exposures.

## Roles

| | Viewer | Editor | Approver | Admin |
| --- | :-: | :-: | :-: | :-: |
| See flags, changes and the audit log | ✓ | ✓ | ✓ | ✓ |
| Create and edit flags | | ✓ | ✓ | ✓ |
| Change configs where no approval is needed | | ✓ | ✓ | ✓ |
| Request changes where approval is needed | | ✓ | ✓ | ✓ |
| Approve or reject other people's requests | | | ✓ | ✓ |
| Projects, environments, SDK keys, users | | | | ✓ |

Nobody approves their own change request, whatever their role.

## How it fits together

```
 browser ──cookie──▶ /api/v1 ─┐                        ┌─▶ Redis: snapshot ─▶ /sdk/v1/flags
                              ├─▶ Postgres ─▶ outbox ─▶ Kafka ─▶ worker ─┤
 SDK ──bearer key──▶ /sdk/v1 ─┘   (one transaction)     flag-changes     └─▶ Redis pub/sub ─▶ /sdk/v1/stream (SSE)

 SDK ──▶ POST /sdk/v1/exposures ─▶ Kafka exposures ─▶ worker ─▶ hourly counts in Postgres
```

- **A flag change** writes the new config, an audit event and an outbox row in one transaction. The worker claims outbox rows with `FOR UPDATE SKIP LOCKED` and sends them to Kafka. It also consumes them: for each change it rebuilds that environment's snapshot in Redis and announces it on pub/sub, which every API instance forwards to its SSE clients.
- **Configs are versioned.** Every change sends back the `version` it loaded as `base_version`; a stale one gets a 409. A change request records its base version too, so approving one after the config has moved on marks it `conflicted` instead of overwriting.
- **Evaluation** is deterministic: rules are checked top to bottom, and percentage rollouts hash `flag/key` with xxhash into 100 buckets, so the same user keeps the same variant.
- **Sessions** live in Redis behind a signed cookie, with a 7-day idle limit and a 30-day absolute limit. Passwords use argon2id. Sign-in is rate limited per email and IP. Every unsafe request carries a CSRF token (a double-submit cookie).

### Code

```
api/
  cmd/api, cmd/worker, cmd/flagpole    the three binaries (flagpole: migrate, seed, admin create)
  db/migrations, db/queries            goose migrations and sqlc queries
  internal/
    identity/      users, sessions, passwords, invites, roles; the auth middleware
    projects/      projects, environments, SDK keys
    flags/         flags, configs, change requests
    rules/         targeting rules and evaluation (no I/O)
    evaluation/    the SDK API: snapshots, evaluate, exposures, stream
    insights/      audit log and exposure counts
    worker/        outbox relay and Kafka consumer
    platform/      config, postgres, redis, kafka, mail, events, HTTP errors
    server/        wires the modules into one Zinc app
    e2e/           end-to-end tests against the real containers
web/               React, Vite, TanStack Router and Query, Tailwind
```

Each module owns its routes: it has a `Routes` method that takes the groups to register on, and `server` decides where those groups are mounted. Modules talk to each other through small interfaces, such as the snapshot invalidator that `flags` calls.

### Zinc in use

- **Typed handlers** (`zinc.Typed`): requests bind and validate from struct tags, and invalid input comes back as RFC 9457 problems with one message per field.
- **Groups with guards**: `/api/v1` carries the session, CSRF and auth middleware; routes add `RequireRole(...)`, and `/sdk/v1` carries CORS and the SDK key check.
- **Generated OpenAPI**: `.Tags`, `.Errors`, `.RequestExample`, `.Produces` and enum types describe the API, which serves its own OpenAPI 3.1 spec and reference page. Every route has an `operationId` from `.Name`. The role a route needs is a scope on the session scheme, such as `.Security("session:editor")`, so the spec documents the 403. `SchemaNamer` names the request and response schemas, and `pattern` tags check and document the key formats. `Document` adds what the CSRF and timeout middleware do: the CSRF token as a security scheme on unsafe requests, and their errors. A test reads the spec and checks each route's guard refuses the role below the one it names. The dashboard's TypeScript types come from the spec (`make types`).
- **Middleware**: requestid, logger, recover, secure headers, timeout, session, csrf, cors, prometheus and healthcheck.
- **Server-sent events** with `c.SSE` for the SDK stream, and **response validation** in development.

## The demo shop

`demo/` is Harbour Supply Co., a small shop that reads its flags from web-app's development environment, where changes apply without review. `make seed` writes its SDK key to `demo/.env.local`; then:

```sh
make demo    # http://localhost:5174
```

Every flag changes something you can see:

| Flag | In the shop |
| --- | --- |
| `maintenance-banner` | A hazard-tape banner across the top |
| `free-shipping-threshold` | The free shipping line: £50 (`standard`) or £25 (`promo`) |
| `search-v2` | Search as you type with suggestions, or the old search that waits for Enter |
| `button-color` | The colour of every buy button: a three-way split by user |
| `new-checkout` | A one-page checkout, or the old three steps |

Open the dashboard beside it, change a flag in the Development tab, and the shop changes within a second: the part the flag controls flashes, with the flag's name. The panel in the corner shows who you're browsing as, each flag's variant and why, and the changes as they arrive. Switch between Ada (UK, pro), Bram (Netherlands, free), Chen (US, team) and an anonymous visitor to see rules target them; "new visitor" picks a new key, which can land in a different `button-color` bucket. X-ray outlines everything a flag controls.

The shop calls the API directly from the browser, as a customer's site would, with the SDK in `sdk/js`.

## The JavaScript SDK

`sdk/js` is a small TypeScript client with React bindings ([its README](sdk/js/README.md)). It asks the API to evaluate every flag for the current user, re-evaluates when the stream says something changed, and reports exposures in batches. Its tests run against the live stack:

```sh
cd sdk/js && FLAGPOLE_KEY=fp_dev_... npm test   # the key from demo/.env.local
```

## The SDK API

Every SDK call sends an environment's key as `Authorization: Bearer fp_…`.

```sh
KEY=fp_pro_...   # from `make seed`, or Settings in the dashboard

# Every flag in the environment, for evaluating locally. Send the ETag back to get a 304.
curl -H "Authorization: Bearer $KEY" localhost:8080/sdk/v1/flags

# Or let the server evaluate for one user.
curl -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"context": {"key": "user-42", "attributes": {"plan": "pro"}}}' \
  localhost:8080/sdk/v1/evaluate

# Report which variants were served.
curl -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"exposures": [{"flag": "button-color", "variant": "green"}]}' \
  localhost:8080/sdk/v1/exposures

# Hear about changes as they happen.
curl -N -H "Authorization: Bearer $KEY" localhost:8080/sdk/v1/stream
```

## The dashboard

Environments are drawn as signal flags from the International Code of Signals: production flies Papa ("about to sail"), staging Sierra and development Delta. A flag that's on is hoisted up its mast; one that's off is lowered. It follows the system light or dark setting, and the switch at the bottom of the sidebar overrides it.

## Tests

```sh
make up
make test    # unit tests and the end-to-end suite, with -race
make lint    # go vet and staticcheck
```

To check the stack you're running, rather than a test copy of it:

```sh
make prove   # needs make up, api, worker and seed
```

It signs in as each demo user and takes a throwaway flag through a reviewed production change, checking roles, version conflicts, what the SDK evaluates, the live stream, the snapshot ETag, exposure counts, the audit log and key revocation. Then it archives the flag and revokes its key. Set `API=http://localhost:3000` to run it through the containers.

The end-to-end suite runs the API and worker in-process against the real containers, using a separate `flagpole_test` database and Redis database 15. It signs in, works through flags, configs and change requests (including a conflict), reads the SDK snapshot and stream, counts exposures, revokes a key and checks the rate limit.
